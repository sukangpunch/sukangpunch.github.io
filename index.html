문제
  • 앱 서버가 1대라 배포하거나 서버가 죽을 때마다 약 43초 동안 요청을 받을 곳이 없었다
  • 사용자 200명 부하에서 그 구간 요청의 39~42%가 실패(전부 502). 측정 중 우연한 재시작 40초에도 44.38% 실패
  • 43초 = 새 JVM 기동 약 33초 + 데우기 약 9초. 데우기는 차가운 서버에 200명이 한꺼번에 몰린 탓(10초에 요청 475건, 스레드 200개 가득)

  • 서버를 2대로 늘리면 주기 작업 12곳이 서버마다 한 번씩, 즉 두 번 실행되는 문제도 함께 풀어야 했다

개선 과정
  1. 측정"몇 초 끊기나"를 재는 도구부터

    k6 요약은 단계별 합계만 보여 줘서 끊긴 시간을 알 수 없었다. 요청마다 시각 · 상태를 남겨 초 단위 실패 타임라인을 계산하는 도구를 만들고, 자극은 실제 배포 버튼과 kill -9로 넣었다.

    운영 중인 실사용 부부 한 쌍의 일주일 로그에서 뽑은 API별 호출 비율(읽기 87%)에 맞춰 가상 부부 200명으로 재현했다.

  2. 결정ASG 2대 + 한 대씩 교체 + slow start 60초

    대상 그룹에서 한 대씩 빼고 교체하고, 새 서버에는 요청을 천천히 늘려 데우기 공백을 없앴다. 헬스 체크는 30초×3 → 5초×2.

  3. 실패비용을 아끼려 시험한 micro 2대가 함께 무너졌다

    앱 서버는 이미 메모리 문제로 small을 쓰고 있었지만, 2대가 되면 고정비가 두 배라 더 싼 t4g.micro(1GB) 2대안을 일부러 관문 회차로 시험했다. 200명 부하에서 p95 19,061ms, 오류 11.56%, GC 정지 최대 16.4초. ASG가 한 대를 교체하는 5분 동안 남은 한 대가 혼자 받다 무너져 두 대 모두 교체됐다.

    결정t4g.small(2GB) 2대 유지

    한 대당 월 약 $7~8 더 내는 대신 여유를 확보. small 2대는 같은 부하에서 p95 34ms, GC 최대 72ms. 서버 대수와 별개로 "한 대의 크기"를 따로 검증하는 관문을 뒀다.

  4. 발견과부하가 오면 ASG가 멀쩡한 서버를 갈았다

    600 → 1,800명 계단 과부하에서 느려지기만 해야 할 서버가 3번 교체되고, 실패율이 1,200명 단계 13.68%, 1,500명 단계 16.60%까지 올랐다. 헬스 체크가 사용자 요청과 같은 줄에 서서, 바쁜 서버를 죽은 서버로 판단한 것.

    결정헬스를 관리 포트(8090) liveness로 분리

    DB를 보지 않는 liveness로 바꾸고 사용자 포트와 분리. 같은 과부하에서 교체 0번, 실패 0 / 576,465건(느려지기만 함).

  5. 결정비용: on-demand 1 + spot 1, 3대째는 끔
    • spot 회수는 "한 대 장애"로 취급하고 바닥 한 대는 on-demand. 월 약 $11.7 상쇄
    • 자동으로 3대까지 늘려 보니 처리량 +4~11%뿐. DB(micro) CPU 73~82%가 먼저 막아 2대로 고정
  6. 실패spot을 섞은 뒤 배포를 다시 재지 않았다

    배포는 한 대씩 ASG의 standby(쉬는 상태)로 돌리고 새 코드로 바꾸는 방식이었다. spot을 섞은 뒤 on-demand 서버를 standby로 빼자, ASG가 "on-demand 최소 1대" 규칙이 깨졌다고 보고 새 on-demand를 띄우면서 요청을 받던 spot 서버를 종료했다. 그래서 정상 서버가 0대인 시간이 1분 생겼다. spot 종료 테스트만 하고 배포 테스트는 다시 하지 않아 놓쳤다.

    결정ASG는 건드리지 않고 로드밸런서에서만 빼기

    배포할 서버를 대상 그룹에서만 잠깐 빼고 바꾼 뒤 다시 넣는다. ASG는 서버 2대가 그대로라 교체하지 않는다. 같은 구성으로 다시 재서 실패 0 / 35,433건. "구성을 바꾸면 배포도 다시 잰다"를 원칙으로 남겼다.

  7. 결정주기 작업은 한 서버만: DB 한 행을 리더 자리로

    DB의 한 행을 리더 자리로 두고 한 서버가 30초 임대를 10초마다 갱신하며 주기 작업을 맡는다. 리더가 죽어 30초 갱신이 끊기면 다른 서버가 이어받는다. 처음엔 Redis로 리더를 잡았지만, 같이 쓰던 Redis 캐시가 성능에 차이를 내지 못해 리더까지 DB로 옮기고 Redis를 뺐다(월 −$14).

개선 과정
  1. 측정부하 대본부터 세 번 고침
    • 부부 화면이 실제로 부르지 않는 API를 웹 코드와 대조해 뺌
    • 운영 중인 실사용 부부 한 쌍의 일주일 로그(요청 11,664건)로 비율을 맞춤: 읽기 87%. 원래 대본은 사진 상세를 22배, 담기 · 빼기를 30배 부풀렸고, 실제로 가장 많은 목록 조회는 빠져 있었다
    • 대본이 바뀔 때마다 '개선 전'을 다시 쟀고, k6가 빨라지면 더 많이 보내는 점을 감안해 전체 요청 수도 함께 기록(16,737 → 48,559건)
  2. 발견앱의 DB 커넥션 풀(10개)에 모든 요청이 줄을 섬

    앱 서버(Spring Boot)가 DB에 붙을 때 쓰는 커넥션 풀(HikariCP) 10개가 모두 사용 중이었고, 연결을 기다리는 요청이 최대 194개였다.

    • DB에서 1ms면 끝나는 가벼운 조회까지 p95가 9~18초로, 무거운 요청과 거의 같았다. 쿼리가 느린 게 아니라 연결을 얻으려고 같은 줄에 서 있던 것
    • AI 분석을 진행시키는 스케줄러도 같은 줄 뒤에 서서, 임베딩 호출이 분당 128~143건에서 14~46건으로 떨어졌다. 그 결과 업로드부터 AI 폴더 완성까지가 16분 28초로 밀렸다(가드레일 10분 47초)

    풀이 병목처럼 보였다.

  3. 실패풀을 나누고, 늘렸더니 더 나빠짐

    분석용 풀을 따로 두자 12,454ms, 풀을 10 → 20으로 늘리자 30,001ms · 오류 21%. 모든 쓰기가 작업공간 한 행을 잠그고 있었다. 병목은 연결 수가 아니라 행 잠금 경합이었고, 풀을 늘리면 줄이 DB 안으로 옮겨 갈 뿐이었다.

    결정연결을 늘리는 대신, 한 행에 몰리는 앱 쓰기를 모은다

    앱 서버가 요청마다 남기던 갤러리 활동 기록이 전부 작업공간 한 행을 고치고 있었다. 이 기록을 모아서 한 번에 쓰게 바꿔 행 잠금 경합을 줄였다.

  4. 발견다음 벽: AI 임베더 Lambda 72개가 사진마다 직접 DB에 씀

    행 잠금을 풀자 다른 쓰기가 드러났다. pg_stat_statements로 보니 임베더 Lambda 72개가 사진마다 분석 결과 INSERT와 미리보기 UPDATE를 각자 날리고 있었고, 이것이 DB 시간의 56.8%였다. 경합이 아니라 쓰는 주체와 횟수 자체가 많은 문제.

    결정SQS 결과 큐 + writer Lambda

    임베더 Lambda는 결과를 DB에 직접 쓰지 않고 SQS 결과 큐에 넣는다. 별도의 writer Lambda(동시 최대 2개)가 큐에서 10건씩 묶어 가져가 DB에 쓴다. DB에 붙는 쪽이 임베더 72개에서 writer 2개로 줄었다. p95 19,106 → 6,056ms, DB 쿼리 시간 합계 −94%, RDS CPU 88% → 19~41%.

  5. 발견JFR: 앱 CPU의 63.7%가 사진 조회용 presigned URL 생성

    S3에 있는 사진을 브라우저가 직접 받으려면 사진마다 기한이 있는 presigned URL(서명이 붙은 임시 주소)이 필요하다. 사진 목록 한 페이지(200장)를 줄 때마다 같은 사진의 presigned URL을 매번 새로 만들고 있었고, JFR로 보니 이 서명 계산이 앱 CPU 표본의 63.7%였다.

    결정presigned URL 10분 재사용 캐시

    한 번 만든 URL을 10분 동안 다시 쓴다. URL 1,542자 중 사진마다 다른 건 서명 시각과 서명 값뿐이라 공통 부분은 공유하고 둘만 저장했다(항목 약 250B, 캐시 적중 0.44µs vs 새로 생성 102.7µs). p95 6,056 → 51ms.

  6. 결정Lambda가 끝내 실패하면 DLQ로 받아 바로 재처리

    분석 Lambda는 재시도 후에도 실패하면 그 호출을 SQS 실패 큐(DLQ)에 남기도록 하고, 서버가 이 큐를 읽어 실패한 작업을 재전송 대기 시간까지 기다리지 않고 바로 다시 보내게 했다.

    검증장애를 일부러 넣어 재처리 경로 확인

    실제 Lambda 오류율이 높아서가 아니라, 이 경로가 동작하는지 보려고 Lambda 호출의 2%가 받자마자 죽도록 장애를 주입했다. 분류 단계 재처리 1,222초 → 24초, 잃은 작업 0, DLQ에 쌓인 실패 22건을 모두 재처리.

  7. 발견캐시로도 남는 문제: presigned URL은 계속 바뀐다

    서버가 2대가 되면서 두 서버가 캐시를 함께 쓰도록 Redis(Valkey) 공유 캐시까지 붙였다. 그래도 문제가 남았다.

    • presigned URL은 보안상 오래 둘 수 없어 10분마다 바뀌고, 웹은 12분마다 목록을 다시 받아 주소를 모두 갈아 끼웠다. 브라우저는 주소가 바뀐 사진을 새 사진으로 보고 이미 본 사진도 다시 받았다(한 페이지에 1시간 머무는 측정에서 112MB, 주소가 고정이면 13MB)
    • 서명이 바뀔 때마다 캐시도 다시 채워야 했다
    결정미리보기는 CloudFront 고정 주소 + 갤러리 단위 서명 쿠키

    미리보기 이미지를 CDN의 바뀌지 않는 주소로 주고, 볼 권한은 갤러리 단위 서명 쿠키로 확인한다. 주소가 고정이라 브라우저 캐시가 그대로 살고, 서명 URL 캐시와 Valkey는 필요 없어져 걷어냈다.

문제
  • 랭킹 API 4개(리그별 목록, 내 리그 목록, 내 순위, 히스토리)가 요청마다 리그 전체(최대 27만 명)에 순위(DENSE_RANK)를 다시 매겨, 1페이지를 보든 500페이지를 보든 51,146페이지를 읽었다
  • "내 순위" 조회는 나보다 위인 사람을 세는 구조라 내 등수에 비례해 느려졌다
  • 과거에 인덱스와 쿼리 재작성으로 1.5초 → 470ms를 만들었지만, 로컬에서 한 건씩 호출해 잰 값이었고 쓰기 비용은 재지 않았다
  • 경로마다 동점 기준이 달라 같은 유저가 목록에선 1등, 히스토리에선 218등으로 보였다
개선 과정
  1. 측정같은 코드에서 인덱스만 있고 없고를 비교

    레슨을 마칠 때마다 리그 점수가 바뀌는 테이블이라 "인덱스가 쓰기에서 손해 아닌가"가 출발점이었다. 유저 100만 명(실제처럼 리그 15개)으로 실제 HTTP를 보내 비교했다.

    • 조회 p95가 사실상 같았다(목록 520 vs 537ms 등). 읽은 페이지도 51,146 → 51,106으로 그대로, 히스토리 조회는 오히려 93배 악화
    • 과거의 470ms는 인덱스가 아니라 잘라낸 10명만 조인하게 바꾼 쿼리 재작성 몫이었다. 당시 시드가 리그 하나에 100만 명이라 실제 분포와도 달랐다
  2. 발견인덱스는 조회 대신 쓰기를 막고 있었다

    인덱스가 걸린 리그 점수가 바뀌면 PostgreSQL은 행을 제자리에서 고치는 HOT 업데이트를 못 하고 인덱스까지 새로 쓴다. HOT 업데이트 비율이 0%였다.

    결정인덱스 재구성

    레슨마다 바뀌는 리그 점수가 랭킹 인덱스에 들어 있어, 매 업데이트가 인덱스까지 새로 쓰고 있었다. 조회에도 기여하지 않던 이 인덱스를 지우고, 쓰기가 행을 찾을 때 쓰는 user_id 인덱스만 남겼다. 점수를 바꿔도 인덱스를 건드리지 않는 HOT 업데이트가 0% → 95%가 됐고, 업데이트 한 번에 남기는 WAL(변경 기록 로그)이 787.5 → 355.5바이트(약 −55%)로 줄었다.

  3. 결정조회는 구조 문제라 Redis Sorted Set으로
    대안판단
    DB에서 계속 계산하되 인덱스 · SQL 개선조회: "내 순위"는 나보다 높은 사람을 세야 해서 등수만큼 읽는다. 인덱스만 더 걸었을 때 p95 1,086 → 800.9ms로 목표(200ms)에 못 미침
    쓰기: 순위용 인덱스에는 리그 점수가 들어가야 하는데, 이 값은 레슨마다 바뀌어 매번 인덱스를 다시 써야 한다
    Redis Sorted Set (선택)점수 순 정렬을 메모리에서 유지해 내 순위를 바로 꺼내고, 점수 갱신이 DB 쓰기 경로를 무겁게 하지 않는다. 대가는 저장소 2개와 정합성 책임 → 폴백 · 백필로 대응
    • 동점 규칙("같은 점수면 먼저 가입한 사람이 앞")을 점수 하나에 넣음. Redis는 동점이면 멤버를 문자열 순으로 세워 순서가 깨지기 때문. 목록 · 내 리그 · 내 순위 · 히스토리 4개 API가 모두 이 정렬을 읽어 같은 순위를 보게 됨
    • Redis 전용 연결 타임아웃 100ms, 실패하면 DB 조회로 폴백, 기동 시 DB 인원과 대조해 백필
    • 점수 반영은 레슨 제출이 커밋된 뒤에만
  4. 측정조건을 고정해 다시 측정
    • 개선 전 커밋을 그대로 빌드해 해시로 대조, 재시드해도 같은 시드, 1만 · 10만 · 25만 · 30만 · 100만 명
    • 세 구성을 번갈아(ABC · CBA) 5회, 반복 범위가 겹치면 "차이 없음"으로 판정 규칙을 실행 전에 고정
  5. 발견"차이 없음"이던 Redis 비용이 드러나 결론을 정정

    2회 반복에서 "차이 없음"이라 적었던 Redis 동기화 비용이, 5회 반복에서는 범위가 겹치지 않는 쓰기 p95 +3.4ms(+23%)였다. 쓰기 개선의 대부분은 Redis가 아니라 인덱스 재구성 몫이라는 것도 이때 확인했다.

개선 과정
  1. 측정재는 법부터 바꿈

    실제 API의 쿼리 원문을 쓰고, 지표를 실행 시간이 아니라 읽은 페이지 수와 스캔 방식으로, 캐시가 빈 상태와 찬 상태를 나눠, 동시 부하까지 함께 쟀다. 시드도 실제 코드 규칙(닉네임 2~8자, 핸들 8자)을 따라 만들었다.

  2. 발견인덱스가 없거나, 내 쿼리가 인덱스를 막고 있었다
    • 닉네임 인덱스 자체가 없어 테이블 전체를 읽음(5,213페이지, 약 41MB)
    • 새로 만든 커버링 인덱스에 닉네임 컬럼이 빠져 있었음
    • 직접 짠 CTE가 자동으로 분리 실행되면서 검색어가 상수로 취급되지 않아 인덱스를 못 탔음
  3. 실패스캔 방식만 보고 만족했다가, 결과가 틀리는 회귀를 만듦

    코드 리뷰에서 "이 인덱스는 정렬을 지원하지 않아 앞에서 멈추지 못한다"는 지적을 받았다. 필터로 버려진 행 수는 안 보고 "인덱스만 읽는다"는 스캔 방식만 보고 만족했던 것. 고치다 보니 결과가 틀리는 결함 2개가 나왔다.

    • 후보를 고르는 순서와 화면에 보여 주는 순서가 달라 김 검색 1페이지가 20명 중 0명 맞음(첫 개선이 만든 회귀)
    • 정렬 규칙을 바꾼 인덱스는 = 비교에도 같은 규칙을 명시해야 탔음
    결정정렬 규칙을 쿼리와 인덱스에 일치시킴

    닉네임은 COLLATE "C" 인덱스, 핸들은 ORDER BY USING ~<~로 후보 순서와 표시 순서를 맞췄다.

  4. 발견재현 벤치가 배포 직전의 회귀를 잡음

    핸들 검색의 "개선 후" 쿼리가 유니크 인덱스 전체를 읽는 계획(66,846페이지)으로 튀어 개선 전보다 느려져 있었다. 정렬을 맞춰 399페이지로 되돌렸다. 재현 가능한 벤치가 없었다면 그대로 배포됐을 회귀였다.

  5. 측정조건을 고정하고, 검사 도구부터 검증
    • 1만 · 10만 · 30만 · 100만 명, 실제 HTTP 8명 동시 60초, 개선 전후 번갈아 5회
    • 결과가 맞는지 보는 검사가 정말 결함을 잡는지, 결함이 있는 버전을 일부러 넣어 먼저 확인(21개 중 6개 오류를 잡아냄)
  6. 발견측정 절차가 결과를 바꿨다

    쓰기를 잰 뒤 DB를 되돌리려고 VACUUM FULL(테이블을 새로 쓰며 인덱스도 다시 만드는 정리)을 돌렸다. 다시 만든 핸들 정렬 인덱스가 빽빽해져 훑는 비용이 싸게 어림되자, 플래너가 "개선 전" 핸들 검색에서 검색어로 바로 찾던 trigram 인덱스 대신 정렬 인덱스를 처음부터 훑는 계획을 골랐다. 맞는 사람이 드물어 20명을 채우지 못하고 끝까지 읽으면서 74페이지(0.49ms)가 100만 페이지(210ms)가 됐다.

    그대로 비교했다면 개선 효과가 부풀려졌을 것이라, 이 상태에서 잰 5건을 버리고 데이터를 다시 만들었다. 이후 쓰기 측정은 복제한 DB에서만 하고 버렸다.

  7. 발견개선 후에도 남은 예외 하나를 후속 이슈로 분리

    대부분의 검색은 빨라졌지만, 정확히 일치하는 사람이 0명인 검색어(예: 코딩)는 30만~40만 명부터 실행 계획이 바뀌어 다시 느려졌다(100만 명에서 180ms). p95가 TPS만큼 좋아지지 않은 이유다. 플래너가 일치 건수를 0명이 아니라 수천 명으로 잘못 어림한 것이 원인이고, 통계를 보강하면 0.045ms로 해결되는 것까지 확인한 뒤 적용은 후속 이슈로 분리했다.

개선 과정
  1. 측정로컬에서 재현부터

    로컬 Docker Compose, 테스트 데이터, 재현 스크립트 5종(새로고침, 동시 구독, 메모리 관찰 등)을 만들었다. curl -N으로 SSE 4개를 연 뒤 클라이언트를 강제로 죽여도(SIGKILL) 서버의 연결 객체(Emitter)는 4개 그대로였다. 서버가 끊김을 모르고 있었다.

  2. 발견배포 서버에서 어느 구간이 막혔는지 확인, 원인 3겹

    배포 EC2에서 lsof -i :8080으로 소켓을 구간별로 셌다. Nginx와 Docker 프록시 사이는 정상 연결이었고, Docker 프록시 → 컨테이너 구간이 FIN_WAIT2였다. 프록시는 닫자고 보냈는데 컨테이너 안 Spring이 소켓을 닫지 않고 있었다.

    • Spring은 써 보기 전엔 끊김을 모른다: 연결이 끊겨도 30분 타임아웃만 기다림
    • 평소에 보내는 게 없다: 참석자 수가 바뀔 때만 전송하니 끊김을 알려 줄 쓰기 실패(IOException)도 없음
    • Nginx가 1시간 붙잡는다: 팀 프로젝트 때 "연결되자마자 끊김"을 막으려 넣은 proxy_read_timeout 3600s가 그대로 남아 있었음

    프론트에서도 새로고침할 때 보내는 구독 해제 요청이 페이지가 닫히며 취소되고 있었다.

  3. 발견팀 프로젝트 때의 대책이 다른 사람의 연결을 끊고 있었다

    연결을 행사 하나에 하나만 저장해서, 같은 행사 화면을 두 번째 운영자가 열면 첫 번째 연결이 닫혔다. 브라우저는 끊기면 자동으로 다시 연결하니 두 화면이 서로를 계속 끊었다 → 행사별 · 사용자별로 연결을 나눠 저장하도록 바꿨다.

  4. 실패타임아웃만 줄여서는 바로 정리되지 않았다
    • Nginx 3600초 → 60초, 45초마다 heartbeat를 보내게 했지만, 다시 재 보니 결과가 같았다. 타임아웃이나 heartbeat 주기가 돌아야만 소켓이 사라졌다
    • 타임아웃이 지나면 결국 정리되긴 한다. 하지만 새로고침 약 10회에 27개가 남았으니, 여러 사람이 새로고침을 반복하면 타임아웃 1분 안에도 수백 개가 쌓여 다시 서버가 멈출 수 있다
    • SSE 타임아웃을 무제한으로 바꿨다가 되돌렸다. 타임아웃 콜백이 영원히 불리지 않아, 쓰기 실패가 없으면 연결이 저장소에 영구히 남기 때문
    • → 기다려서 치우는 방식이 아니라, 나갈 때 바로 해제하는 방식이 문제라고 다시 봤다
  5. 결정구독 해제를 complete() 대신 completeWithError()로

    구독 해제 요청이 오면 연결을 바로 해제하게 바꾸고, 전송 실패 · heartbeat 실패 경로도 같은 방식으로 통일했다. 프론트는 페이지를 떠날 때(pagehide) 해제 요청이 취소되지 않게(keepalive) 함께 고쳤다.

  6. 검증heartbeat는 보험, 끄고 켜서 배포해 비교

    브라우저 강제 종료나 네트워크 단절처럼 해제 요청이 아예 오지 않는 경우는 heartbeat만 잡을 수 있다. heartbeat를 끈 버전과 켠 버전을 차례로 배포해, SSE를 강제로 끊고 100초 뒤 소켓을 비교했다. Nginx는 heartbeat 45초보다 긴 80초로 맞췄다.

트랜잭션 밖 Redis · SSE 실패를 지점별 정책으로 나눠 참석자 수 정합성 복구

DB 저장이 실패해도 Redis 참석자 수는 +1로 남고, 화면 전송 실패는 DB 저장까지 막음 → 실패 지점마다 다른 정책 + 보상 롤백 + 실패 큐 재처리 → 통합 테스트 16개로 검증

문제
  • 얼굴 인증 뒤 비동기 스레드 하나에서 ① Redis 저장(참석 목록, 참석자 수 +1) → ② SSE 전송 → ③ DB 저장을 실패 처리 없이 순서대로 실행했다
  • ③이 실패하면 참석자 수는 +1인데 DB에는 참석 기록이 없는 상태가 영구히 남는다
  • ②가 실패하면 예외가 그대로 던져져 ③이 아예 실행되지 않았다. 화면 전송 실패가 참석 기록 유실로 번지는 구조
  • 비동기 예외는 호출부로 올라오지 않아, 어떤 참석 건이 실패했는지 알 수 없었다
개선 과정
  1. 발견Redis · SSE는 DB 트랜잭션에 묶이지 않는다

    비동기 여부와 상관없이 Redis와 SSE는 DB 트랜잭션 밖이라, DB가 롤백돼도 따라 되돌아가지 않는다. 고치기 전에 두 문제(카운트만 남음, SSE 실패로 DB 미저장)를 테스트로 먼저 재현했다.

  2. 결정실패 지점마다 다른 정책

    "어디서 실패했을 때 무엇이 어긋나는가"를 기준으로 나눴다.

    실패 지점처리이유
    Redis 저장즉시 중단Redis도 DB도 반영 전이라 이미 일관됨
    SSE 전송경고 로그만 남기고 진행화면 갱신용이라 정합성과 무관, DB 저장을 막으면 안 됨
    DB 저장Redis 보상 롤백 + 실패 큐 적재Redis만 반영된 상태를 되돌리고, 나중에 다시 저장
    Redis 롤백 자체CRITICAL 로그자동 복구 불가 → 사람이 확인
  3. 결정되돌리기만 할지, 다시 저장까지 할지
    대안판단
    Redis 롤백만참석자 수는 맞지만, 그 참석 기록은 DB에 끝내 저장되지 않음
    이벤트 저장소(EventStore) 도입최소 한 번 처리를 보장하지만 이벤트 저장소를 새로 둬야 함
    Redis 롤백 + Redis 실패 큐 + 재처리 (선택)롤백으로 숫자를 맞추고, 실패한 이벤트는 이미 쓰는 Redis에 보관했다가 다시 저장
  4. 결정실패 큐를 비우는 재처리 스케줄러

    큐에 넣기만 하면 다시 저장되지 않으니, 꺼내서 처리하는 쪽을 함께 만들었다. 60초마다 50건씩 꺼내 DB에 다시 저장하고, 성공하면 큐에서 지운다.

  5. 결정비동기 예외에 어떤 참석 건인지 남김

    기본 예외 처리기는 메서드 이름만 남겨 어떤 참석 이벤트가 실패했는지 알 수 없었다 → 이벤트 파라미터까지 로그에 남기는 전역 비동기 예외 처리기로 바꿨다.

  6. 검증실제 Redis로 실패를 주입하는 통합 테스트 16개

    Redis는 Testcontainers로 실제 컨테이너를 띄우고, DB 저장 실패만 주입했다. 롤백 → 큐 적재 → 재처리 순서로 참석자 수가 맞게 돌아오는지 확인했다.

문제
  • 얼굴 인증 뒤 후처리 3개(Redis 저장, SSE 전송, DB 저장)가 끝나야 응답이 나갔다
  • 스레드 이름을 찍어 보니 인증부터 이벤트 처리까지 전부 요청 스레드(http-nio-8080-exec-*) 하나에서 돌았다. Spring 이벤트 리스너는 기본이 동기 실행이다
  • 서비스의 목적은 빠른 입장이라, 후처리는 응답 뒤에 끝나도 된다
개선 과정
  1. 결정후처리를 @Async @EventListener로 응답 경로에서 분리

    인증은 이벤트만 발행하고 바로 응답하고, 후처리는 별도 스레드에서 처리한다. 대가로 응답과 후처리가 더는 함께 성공하거나 함께 실패하지 않는다.

  2. 결정기본 실행기 대신 전용 스레드 풀
    • 기본 SimpleAsyncTaskExecutor는 작업마다 새 스레드를 만든다 → ThreadPoolTaskExecutor를 직접 구성
    • 측정 당시엔 고정값(기본 20, 최대 100, 큐 500)이었고, 개발 PC(16코어)와 EC2(vCPU 1)의 차이를 보고 CPU 수 기준으로 바꿈: 기본 max(2, N), 최대 max(4, N×3), 큐 50
  3. 결정비동기 스레드에서도 같은 요청 ID로 로그 추적

    요청마다 붙이는 TraceId(MDC)는 스레드에 묶여 있어 비동기 스레드로 넘어가면 사라진다 → TaskDecorator로 작업을 넘길 때 함께 복사하고, 작업이 끝나면 비우게 했다.

  4. 측정후처리 500건이 끝나기까지 걸린 시간 비교

    외부 의존을 빼고 후처리만 비교하려고 Rekognition과 DB 조회를 Mock으로 바꾸고 로컬에서 쟀다. 인증 500건을 보내고, 500건의 참석 기록이 모두 저장될 때까지의 시간을 동기(스레드 1개)와 비동기(스레드 풀)로 비교했다.
